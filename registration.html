Case Study — 04
Live · CyberLogitec production · internal, no public demo

A spreadsheet ran the assessment. Now L&D ships events without asking engineering.

CyberLogitec's L&D team booked its English assessment out of a shared sheet, then out of a page hard-coded for that one exam. I turned it into an event platform: L&D opens a training, workshop or assessment themselves, employees enter their details once, and a seat can't be handed to two people, even when an announcement sends a thousand of them at the same minute.

The mechanism

So who gets the seat? In a sheet, everyone does

The dropdown is data validation: it checks that your cell holds one of the allowed values. It has no idea how many other cells already hold that same value. And two people typing into two different rows aren't editing the same cell, so the spreadsheet sees no conflict at all. There is nothing to arbitrate.

In the sheet · two people, same second
13:42:07Minh picks 13:30 – 14:30 in row 7accepted
13:42:07Lan picks 13:30 – 14:30 in row 8accepted
— later —someone reads the sheet and counts7 in 6
— later —emails one of them to movemanual
▪ Different cells, so no conflict exists to detect
▪ Nobody is rejected. Every edit succeeds
▪ The clash surfaces hours later, to a human
In the platform · same second
13:42:07Minh claims the last seatheld
13:42:07Lan claims the same seatrefused
13:42:07Lan is offered the next free sloton screen
—nothing left for anyone to reconciledone
✦ The seat is the document, so a second create cannot exist
✦ Exactly one wins, decided inside the write
✦ The other person knows before they walk away

You can bolt a COUNTIF rule onto the cell. It still reads, then writes, with no lock in between, so two people clicking in the same second both read “space left” and both pass. Validation is not arbitration.

What changed

A sheet, then a one-off page, then a platform

The first rewrite did fix the counting, but only for that one exam. It was hard-coded down to the branding, so the next program meant another build, coordinated with IT, on IT's timeline.

BEFORE — SHEET, THEN A ONE-OFF PAGE
▪ Details re-typed on every registration
▪ Same slot claimable twice; seats-left was a guess
▪ Change or cancel = email L&D, wait for a human
▪ Confirmation only when someone got around to replying
▪ Who's allowed in, reconciled by hand afterwards
▪ A new program = a new build, on IT's schedule
AFTER — ONE PLATFORM L&D OPERATES
✦ Profile captured once at first login, auto-filled after
✦ Seats claimed atomically, so overselling is impossible
✦ Employees book, change and cancel themselves, instantly
✦ Confirmation email fires on the successful write
✦ Allowlist + blocklist enforced by the system, not memory
✦ Any training, workshop or assessment, with no rebuild

Part 2 — under the hood

Three flows, three load shapes, three different locks

The interesting decision wasn't picking a concurrency pattern. It was measuring each flow and refusing to use the same one everywhere, then writing down why, so the next reviewer doesn't "fix" the odd one out.

Simple event
Land rush
One announcement puts ~1000 people on a small seat pool inside the same minute.
↓ a shared counter would serialize at ~1 write/sec
capacityClaims/000000…
Capacity becomes N documents, one per seat. Each caller walks its own shuffled order, so the crowd spreads instead of piling on one doc.
Slotted assessment
Multi-day window
Measured from the previous run: ~72 registrations over 7 days, peak ~1.3/min across ~24 slots.
↓ 40–50× under the contention threshold
slot.remaining -= 1
A plain counter in a transaction, kept deliberately. Migrating it would rewrite correctness-critical seat math to solve contention this traffic never produces.
Employee identity
Uniqueness
One employee code may hold at most one place in a given event, across every account they own.
↓ not a volume problem, an identity one
empCodeClaims/{empCode}
The contended identity becomes the document id, so a duplicate create fails atomically. This is what locks the field in screen 3.

The rule underneath all three: make the contended thing the document id and let create-if-absent arbitrate, never a shared counter, unless the measurement says the counter is free.

Who gets in

One priority order, evaluated twice

"Right people in, wrong people out" used to be reconciled by hand after the fact. Now it's a fixed order of checks, and the client is never trusted with the verdict.

01
Permanent block
Rejected
Platform-wide. Set once by an admin, applies to every event, reason shown to the person.
02
Per-event blocklist
Rejected
Excluded from this event only, typically a no-show from the previous round.
03
Per-event allowlist
Gated
Read only when the event opts into it. Gated employees still see the event, locked rather than hidden, so they know it exists.
04
Employee-code claim
Taken
Has this employee code already taken a place in this event under another account?
✓ Eligible · seat claim proceeds inside the transaction
Run once as a preflight so the button never appears for someone who can't register, then run again inside the write. Passing the first check is not permission to write.
Why it's solid

Server-side by default, verified not assumed

01
Nothing trusts the client
All seat-path writes run inside Cloud Functions transactions in asia-southeast1; Firestore security rules block direct client writes entirely, so the gate and the seat math can't be routed around.
02
Defense in depth
App Check + reCAPTCHA v3 gates every callable, per-user rate limiting on top, and an immutable audit trail on every admin and booking action.
03
Side effects can't invalidate the action
Confirmation mail is queued for the Trigger Email extension, not sent inline; a failed audit or email write is reported through monitoring but never rolls back a seat the employee legitimately claimed.
04
Verified, not assumed
400+ tests across unit and Firestore-rules-emulator suites, plus a security audit that came back 0 Critical/High/Medium findings.
The half that made it a platform

L&D opens an event without opening a ticket

The admin console is the reason this stopped being a one-off. Everything that used to require a developer is a form now.

✓ Create an event: details, cover image, markdown description, capacity, deadline
✓ Choose the shape: one seat per person, or timed slots with configurable exam parts
✓ Stage it unlisted, check it, then flip listed + enrollment open
✓ Paste an eligibility list; block a code per-event or platform-wide, with the reason
✓ Per-event email templates and sender identity, no redeploy
✓ Export the roster to CSV, reconcile capacity, read the audit log

Adding an admin is a field in Configuration, not a deploy, and the console refuses to let you remove your own access.
