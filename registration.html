The problem

Scattered forms, real double-booking risk

L&D needed to register employees for trainings and assessments, and separately run a recurring weekly instructor-booking program — without a form that re-asks the same profile info every time, and without two people accidentally claiming the same seat or the same trainer slot under real concurrent use.

What I built — two live flows
FLOW 1 · EVENT REGISTRATION
Simple & slotted events

Simple events (1 seat, 1 step) and slotted events (pick a timed exam slot, configurable Exam Parts per event). Every seat claim is a single Firestore document created inside a transaction — a duplicate id is rejected outright, so the same seat can't be claimed twice even if 100 people click at once.

GUARDRAILS
✓ Eligibility checked twice — preflight, then re-enforced inside the transaction
✓ 3-layer gate: permanent block → per-event blocklist → per-event allowlist
✓ Employee-code + email dedup — one person, one seat per event
FLOW 2 · PRONUNCIATION PROGRAM
Weekly instructor booking

A single trainer's weekly calendar, booked by a PIC (Person In Charge) on behalf of their class. Each session's document id is date_startMin — a global lock, so a given date + time slot can hold exactly one session company-wide.

GUARDRAILS
✓ Monthly cap (4) + weekly cap (2) per class, enforced server-side
✓ Blackout dates/slots block booking for everyone — including admins, no bypass
✓ Registration window + deadline locks self-service after cutoff
The detail that matters

Zero-input confirm

TYPICAL EVENT FORM
— Re-enter employee code, name, business unit every time
— No feedback on whether you already hold a seat
— Concurrent submits can silently conflict
THIS PLATFORM
✓ Profile completed once at first login — every later registration is a single confirm
✓ Seat claim is atomic — Firestore rejects the duplicate, no oversell
✓ Eligibility resolved before the user even sees the register button
Why it's solid

Server-side by default, verified not assumed

01
Nothing trusts the client
All money-path writes run inside Cloud Functions transactions in asia-southeast1; Firestore security rules block direct client writes entirely.
02
Defense in depth
App Check + reCAPTCHA v3 gates every callable, rate limiting on top of that, and a full audit log on every admin and booking action.
03
Verified, not assumed
400+ tests across unit and Firestore-rules-emulator suites, plus a security audit that came back 0 Critical/High/Medium findings.
