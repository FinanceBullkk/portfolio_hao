L&D Event Registration Platform

React · Firebase · Cloud Functions

Internal Platform for Event Booking & Capacity Control

An L&D team was booking an assessment from a shared sheet and a page hard-coded for one exam. I shaped that workflow into a reusable event platform: L&D can configure a training, workshop or assessment, employees can save details for reuse, and capacity and eligibility are checked in the write path.

Problem

Shared-sheet booking made capacity and eligibility reconciliation manual.

Role

Workflow design, React/TypeScript implementation and Firebase data rules.

Result

A configurable flow that gives operators a visible, reviewable path from event setup to confirmation.

The mechanism

So who gets the seat? A sheet can accept both rows

The dropdown is data validation: it checks that your cell holds one of the allowed values. It has no idea how many other cells already hold that same value. And two people typing into two different rows aren't editing the same cell, so the spreadsheet sees no conflict at all.

What changed

A sheet, then a one-off page, then a platform

The first rewrite did fix the counting, but only for that one exam. It was hard-coded down to the branding, so the next program meant another build, coordinated with IT, on IT's timeline.

BEFORE — SHEET, THEN A ONE-OFF PAGE
▪ Details re-typed on every registration
▪ Same slot claimable twice; seats-left was a guess
▪ Change or cancel = email L&D, wait for a human
▪ Confirmation only when someone got around to replying
▪ Who's allowed in, reconciled by hand afterwards
▪ A new program = a new build, on IT's schedule
AFTER — ONE PLATFORM L&D OPERATES
✦ Profile captured once at first login, auto-filled after
✦ Atomic seat claims are designed to reject overselling in the write path
✦ Employees can book, change and cancel from the self-service flow
✦ Confirmation email fires on the successful write
✦ Allowlist + blocklist enforced by the system, not memory
✦ Configurable training, workshop, and assessment types without a one-off page rebuild

Part 2 — Under The Hood

Three flows, three load shapes, three different locks

The design decision was modelling each flow separately instead of applying one concurrency lock everywhere, then documenting the assumption so future maintainers know what must be validated.

Land rush
Illustrative load shape: concurrent registrations may converge on a small seat pool.
↓ a shared counter can become a contention point
capacityClaims/000000…
Capacity becomes N documents, one per seat. Callers walk shuffled order to disperse write contention.
Slotted assessment
Multi-day window
Design assumption: a spread-out assessment window has a lower, more predictable write rate across its slots.
↓ below the expected contention threshold
slot.remaining -= 1
Plain counter in a transaction, kept deliberately for a flow designed around a lower, predictable write rate.
Employee identity
Uniqueness

↓ identity arbitration problem
empCodeClaims/{empCode}
The identity becomes document id, so a duplicate create fails atomically.
Eligibility Governance

One priority order, evaluated twice

"Right people in, wrong people out" used to be reconciled by hand after the fact. Now it's a fixed server-side order of checks.

01
Permanent block
Rejected
Platform-wide. Set once by an admin, applies to each event, reason shown to the person.
02
Per-event blocklist
Rejected
Excluded from this event only, typically a no-show from the previous round.
03
Per-event allowlist
Gated
Read only when the event opts into it. Gated employees still see the event, locked rather than hidden.
04
Employee-code claim
Taken
Has this employee code already taken a place in this event under another account?
✓ Eligible · seat claim proceeds inside the transaction
Preflight check controls button display; full re-check runs inside the atomic write.
Security & Resilience

Server-side by default, verified not assumed

01
Server-side write path
The design places seat-path writes inside Cloud Functions transactions in asia-southeast1; Firestore rules are intended to block direct client writes.
02
Defense in depth
The intended boundary combines App Check, reCAPTCHA v3, per-user rate limiting, and audit records for admin and booking actions.
03
Side effects are isolated from the claimed seat
Confirmation mail is queued for the Trigger Email extension, not sent inline; the design keeps a failed email write from rolling back a claimed seat.
04
Verified, not assumed
Unit and Firestore-rules-emulator suites are part of the verification path. Test counts and security-review findings remain owner evidence to attach before a production claim.
Operations

L&D can configure an event without a new ticket

The admin console is designed to turn recurring developer handoffs into configurable fields. Many changes become a form instead of a code request.

✓ Create an event: details, cover image, markdown description, capacity, deadline
✓ Choose the shape: one seat per person, or timed slots with configurable exam parts
✓ Stage it unlisted, check it, then flip listed + enrollment open
✓ Paste an eligibility list; block a code per-event or platform-wide, with the reason
✓ Per-event email templates and sender identity, no redeploy
✓ Export the roster to CSV, reconcile capacity, read the audit log

Adding an admin is a field in Configuration, not a deploy, and the console refuses to let you remove your own access.
